# 오공고 배포 검증

이 문서는 잘못된 시크릿이나 설정이 운영 서비스를 죽이지 못하게 막는 장치를 설명합니다.
배포 워크플로(`.github/workflows/deploy-ecs.yml`)를 고치기 전에 읽습니다.

## 문제

운영 설정은 저장소에 없습니다. `application.yml`은 `.gitignore` 대상이고, 배포 시
GitHub 시크릿 `APPLICATION_SECRET_USER` / `APPLICATION_SECRET_ADMIN`의 내용을 그대로
파일로 써서 jar에 넣습니다.

시크릿을 등록하지 않거나 값이 틀려도 jar와 이미지는 잘 만들어집니다. 문제는 ECS에서 컨테이너가
뜬 다음 드러나고, 그때는 이미 운영 서비스가 죽은 뒤입니다.

## 검증 순서

되돌리기 어려운 단계일수록 뒤에 둡니다. 앞 단계가 실패하면 ECR에 이미지를 올리지도,
ECS를 건드리지도 않습니다.

| 순서 | 단계 | 잡는 것 |
| --- | --- | --- |
| 1 | 필수 시크릿 확인 | 비어 있음, 값 잘림, 공백·줄바꿈 혼입, 사용자·관리자 컨테이너 이름 뒤바뀜 |
| 2 | AWS 자격 증명·리소스 확인 | 만료·오타 난 자격 증명, 없는 ECR 리포지토리·ECS 클러스터·서비스 |
| 3 | 태스크 정의 점검 | 태스크 정의에 없는 컨테이너 이름, 없는 SSM·Secrets Manager 참조 |
| 4 | jar·이미지 빌드 | 컴파일 오류 (여기까지 AWS 상태를 바꾸지 않음) |
| 5 | 컨테이너 기동 검증 | 운영 설정으로 스프링 컨텍스트가 실제로 뜨지 않는 원인 |
| 6 | ECR 푸시 → ECS 배포 → 스모크 테스트 | 실제 트래픽 처리 여부 |
| 7 | 실패 시 자동 롤백 | 위를 다 통과하고도 실패한 경우의 피해 |

### 설정 파일 내용은 배포 전에 검사하지 않습니다

- 결정일: 2026-09-11
- 리뷰 상태: 팀 리뷰 필요

**배경.** 이전에는 모듈별 설정 계약(`.github/config-schema/<모듈>.yml`)으로 허용 키와 값 규칙
(필수 키, `server.port` 값, 형식, `localhost` 금지 등)을 검사했습니다.

**변경 이유.** 설정은 코드와 함께 계속 바뀌는데, 계약을 같이 고치지 않으면 코드에 문제가 없어도
배포가 멈췄습니다. 실제로 관리자 설정에 `spring.data.redis`가 들어 있고 `server.port`가 계약과
다르다는 이유로 배포가 막혔습니다.

키 목록 없이 YAML 문법만 보는 방식도 검토했지만 얻는 것이 적었습니다. 들여쓰기가 밀려 키가
다른 부모 아래로 들어가도 YAML로는 유효하고, 스프링은 모르는 키를 무시하고 기본값으로 뜨기 때문에
정작 막고 싶은 사고는 파일만 봐서는 가려낼 수 없습니다. 그래서 설정 파일 검사를 모두 없앴습니다.

**영향 범위.** 배포 워크플로의 설정 파일 검사 단계, PR의 `Deploy checks` 잡,
`.github/config-schema/`와 검사기 스크립트 삭제. 설정 키를 추가하거나 바꿔도 배포 쪽을 고칠
필요가 없습니다.

**설정이 틀렸을 때 드러나는 시점.**

| 경우 | 드러나는 시점 |
| --- | --- |
| 설정이 틀려 컨텍스트가 뜨지 않음 (필수 빈 생성 실패, 바인딩 실패, 짧은 JWT 키 등) | 5번 기동 검증. 이미지를 푸시하지 않고 멈춥니다 |
| 운영 DB·Redis 주소·계정이 틀리거나, 들여쓰기가 밀려 무시되거나, `localhost`가 남음 | 6번. 새 태스크의 `/health`가 503이라 트래픽을 받지 못하고 배포가 실패해 7번 롤백. 5번은 접속 정보를 CI 값으로 덮어써 통과합니다 |
| 컨테이너 포트가 태스크 정의·ALB 타겟 그룹과 다름 | 6번 스모크 테스트와 7번 롤백. 5번은 포트를 8080으로 덮어씁니다 |
| DB·Redis 외의 키가 무시되고 기본값으로 동작 (메일, 타임아웃 등) | 배포 뒤 해당 기능을 쓸 때 |

### 5번 컨테이너 기동 검증

방금 만든 이미지를 운영 설정으로 띄워 `/health`가 200을 줄 때까지 기다립니다. 빈 생성 실패나
`@ConfigurationProperties` 바인딩 실패처럼 기동 시점에만 드러나는 오류를 이미지 푸시 전에 잡습니다.

예를 들어 `ogonggo.auth.jwt.secret`이 HS512 최소 길이에 못 미치면 jjwt가
`OgonggoTokenProvider` 생성자에서 `WeakKeyException`을 던집니다. 빌드는 통과하고
컨테이너만 죽는 종류의 오류인데, 5번이 이것을 잡습니다.

러너는 VPC 안의 RDS·ElastiCache에 닿을 수 없으므로, 기동 검증은 CI가 띄운 MySQL·Redis
컨테이너를 보게 하고 접속 정보만 환경변수로 덮어씁니다. `ddl-auto`도 `update`로 덮어씁니다.
운영이 `validate`여도 빈 CI DB에는 스키마가 없기 때문입니다. 덕분에 JPA 매핑으로 스키마를
만들 수 있는지까지 함께 확인됩니다.

**덮어쓰는 값은 검증 대상에서 빠집니다.** 운영 DB·Redis 주소와 계정, `server.port`는 5번에서
확인되지 않고 6번 스모크 테스트에서야 드러납니다. 이 구간이 자동 롤백을 남겨 둔 이유입니다.

### 헬스 체크 `/health`

ALB 헬스 체크, 5번 기동 검증, 6번 스모크 테스트가 모두 `/health`를 봅니다. 프로세스가 떴는지가 아니라
요청을 처리하는 데 꼭 필요한 의존성에 실제로 붙는지 확인하고, 하나라도 붙지 못하면 503을 돌려줍니다.

| 모듈 | 확인하는 항목 |
| --- | --- |
| `ogonggo-api-user` | DB, Redis |
| `ogonggo-api-admin` | DB |

Spring Boot Actuator의 헬스 항목(`db`, `redis`)을 컨트롤러가 골라 확인합니다. 확인할 항목을 운영
설정 파일이 아니라 코드에 두는 이유는 `application.yml`이 배포 때 시크릿으로 통째 덮어써지기 때문입니다.
경로가 그대로 `/health`라 ALB 타겟 그룹 설정을 바꿀 필요가 없습니다.

- Redis는 처음 사용할 때 연결하므로 기동만으로는 설정 오류가 드러나지 않습니다. 헬스 체크가 Redis에
  직접 PING을 보내므로, Redis 설정이 틀린 새 버전은 트래픽을 받지 못합니다.
- 메일(SMTP)·디스크는 넣지 않습니다. 잠깐 느려도 서비스가 돌아가는데, 넣으면 그 지연 하나로 모든 태스크가
  트래픽에서 빠집니다.
- 인증 없이 열린 경로라 응답에는 항목별 `UP`/`DOWN`만 담고 오류 내용이나 접속 주소는 담지 않습니다.
- `/actuator/**` 경로는 Security 설정에서 열지 않으므로 외부에서 호출할 수 없습니다.

**운영 영향.** 배포와 무관하게 RDS나 ElastiCache가 장애를 일으키면 모든 태스크가 비정상이 됩니다.
ALB는 모든 타겟이 비정상이면 전체 타겟으로 요청을 계속 보내지만, ECS는 ALB 헬스 체크에 실패한 태스크를
교체하므로 장애가 이어지는 동안 태스크 재시작이 반복될 수 있습니다. 서비스의 헬스 체크 유예 시간
(health check grace period)은 **확인 필요**입니다.

### 7번 자동 롤백

1~5번을 모두 통과하고도 배포나 스모크 테스트가 실패했다면, 러너에서 재현할 수 없는 원인
(보안 그룹, 태스크 역할 권한, VPC 안의 DB 접속 실패, 컨테이너 포트 불일치 등)입니다.
새 리비전을 그대로 두면 서비스가 죽은 채로 남으므로, 배포 직전에 서비스가 실행 중이던
태스크 정의로 되돌리고 헬스 체크가 회복되는지 확인합니다.

롤백에 성공해도 워크플로는 실패로 남깁니다. 배포는 이루어지지 않았기 때문입니다.

## 시크릿 값이 로그에 남지 않게 하는 방법

기동 검증이 실패하면 컨테이너 로그를 200줄까지 출력합니다. 그 로그에 DB 비밀번호나 JWT 키가
그대로 남지 않도록, 워크플로는 기동 전에 `.github/scripts/mask_application_secrets.py`로
민감한 값을 `::add-mask::`에 등록합니다. 이후 단계의 로그에서 그 값은 `***`로 가려집니다.

이 스크립트는 검사가 아니며 어떤 파일이 와도 배포를 막지 않습니다.

- 키 이름에 `password`, `secret`, `key`, `token`, `credential`, `username`이 들어간 값과
  슬랙 웹훅 URL(`https://hooks.slack.com/`)을 등록합니다.
- 8자 미만인 값은 로그가 `***` 범벅이 되지 않도록 등록하지 않습니다.
- YAML로 파싱하지 않고 `키: 값` 모양의 줄을 읽습니다. 들여쓰기가 깨진 파일일수록 스프링이 문제가
  된 줄을 로그에 옮기므로, 파일이 깨져 있어도 값을 가릴 수 있어야 하기 때문입니다.

이 규칙에 걸리지 않는 이름으로 비밀 값을 추가하면 가려지지 않으므로, 그런 키를 추가할 때는
스크립트의 `SENSITIVE_KEY_PATTERN` 또는 `SENSITIVE_VALUE_PATTERN`에 함께 추가합니다.

`APPLICATION_SECRET` 자체는 GitHub이 통째로 하나의 문자열로만 가립니다. 그 안에 들어 있는
개별 값은 자동으로 가려지지 않습니다.

## PR에서 도는 검사

`.github/workflows/test.yml`의 `Deploy checks` 잡이 PR마다 다음을 확인합니다.

- 마스킹 스크립트가 민감한 값을 가리고, 어떤 파일에서도 실패하지 않는지
  (`.github/scripts/test_mask_application_secrets.py`)
- 워크플로 YAML의 문법·표현식 (actionlint)

운영 시크릿 없이 도는 검사라 PR 빌드에서 안전하게 실행됩니다. 로컬에서도 추가 설치 없이 돌릴 수 있습니다.

```bash
python3 .github/scripts/test_mask_application_secrets.py
```

## 아직 잡지 못하는 것

- **운영 DB·Redis·SES에 실제로 붙는지.** 러너는 VPC 안에 들어갈 수 없습니다.
  DB·Redis 연결은 배포 중 새 태스크의 헬스 체크에서, SES는 메일을 보낼 때 드러납니다.
- **ECS 서비스의 배포 설정.** 새 태스크가 헬스 체크를 통과하기 전에 기존 태스크를 내리지 않으려면
  최소 정상 비율(minimum healthy percent)이 100%여야 하고, 실패한 배포를 자동으로 되돌리려면 배포 서킷
  브레이커가 켜져 있어야 합니다. 이 값은 콘솔에서 관리하므로 **확인 필요**입니다.
- **렛츠커리어 서버와의 연동.** `ogonggo.letscareer.internal-api-key`가 렛츠커리어 쪽 값과
  같은지는 확인하지 않습니다.
- **ECS 태스크 정의의 CPU·메모리·네트워크 설정.** 배포는 이미지만 교체하므로 이 값들은
  콘솔에서 관리합니다.
- **두 서비스가 공유하는 스키마의 정합성.** `deploy-main.yml`이 user → admin 순서로
  배포해 동시 스키마 갱신을 피하는 것이 현재의 대응입니다.

## 검증을 끄는 방법

기동 검증과 자동 롤백은 재사용 워크플로의 입력으로 끌 수 있습니다.
긴급 배포처럼 예외 상황에서만 쓰고, 이유를 PR이나 배포 기록에 남깁니다.

```yaml
uses: ./.github/workflows/deploy-ecs.yml
with:
  module: ogonggo-api-user
  startup-verification: false
  rollback-on-failure: false
```
