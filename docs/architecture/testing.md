# 오공고 백엔드 테스트 작성 방식 및 공통 규칙

- 상태: Accepted
- 결정일: 2026-09-15
- 적용 범위: `ogonggo-core`, `ogonggo-api-user`, `ogonggo-api-admin`의 자동화 테스트
- 예상 독자: 백엔드 기능을 구현·수정·리뷰하는 팀원과 코딩 에이전트

## 1. 목적

테스트는 사용자 계약, 도메인 정책, 시스템 불변식이 깨졌을 때 실패해야 한다. 구현 교체나 리팩터링만으로 깨지는 테스트는 유지 비용에 비해 신뢰도가 낮으므로 작성하거나 유지하지 않는다.

테스트는 새 정책, 외부 계약 변경, 실제 회귀, 데이터 무결성 규칙처럼 명확한 근거가 있을 때 추가한다. 아직 정해지지 않았거나 구현하지 않은 정책을 테스트가 임의로 확정해서는 안 된다.

## 2. 공통 작성 규칙

- 하나의 테스트는 하나의 행위 또는 규칙을 설명한다. 여러 결과가 같은 행위의 계약이면 함께 검증할 수 있다.
- 테스트 이름은 구현이 아니라 기대하는 정책 또는 결과를 한국어로 드러낸다. Kotlin 테스트는 현재 프로젝트의 백틱 함수명 스타일을 따른다.
- 준비, 실행, 검증이 구분되는 테스트는 `// given`, `// when`, `// then` 주석을 사용해 의도를 드러낸다.
- 테스트는 다른 실행 순서, 현재 시각, 외부 시스템, 다른 테스트가 남긴 데이터에 의존하지 않는다. 시간 조건은 시간 자체를 검증하는 경우가 아니면 고정 `Clock` 또는 고정 시각을 사용한다.
- 공통 fixture는 필요한 필드만 가진 작은 helper로 만들고, 테스트마다 의미 없는 기본값을 반복하지 않는다.
- 실패 원인이 분명하도록 기대 결과, 예외 타입·ErrorCode, 상태 변화 중 해당 계약에 필요한 것을 직접 검증한다.

## 3. 행동 계약과 구현 상세의 구분

테스트는 호출자가 관찰할 수 있는 결과와 시스템이 지켜야 할 규칙을 검증한다.

- 성공·실패 결과, 응답 필드, 오류 코드, 상태 변화
- 실패 시 발생하면 안 되는 저장·발행·외부 호출 같은 부작용
- 정렬·필터·페이지 처리처럼 API 또는 조회 결과로 드러나는 계약
- 유니크 제약, 참조 무결성, 삭제 정책처럼 DB가 보장해야 하는 불변식

다음처럼 내부 구현만 고정하는 테스트는 피한다.

- private helper의 호출 여부, 내부 호출 순서, 특정 구현체 선택
- Repository 또는 협력 객체에 값을 전달했는지만 확인하는 테스트
- 프레임워크 객체의 구체적 생성 방식이나 중간 자료구조
- mock이 설정한 값을 그대로 반환하는지만 확인하는 테스트

협력 객체 호출 검증은 실패한 요청에서 쓰기가 발생하지 않아야 하거나, 외부 부작용의 발생 여부 자체가 계약인 경우에만 최소 범위로 사용한다. 반환값·예외·상태로 같은 위험을 검증할 수 있으면 그 방식을 우선한다.

## 4. 테스트 계층 선택

| 계층 | 검증 대상 | 원칙 |
| --- | --- | --- |
| 순수 단위 테스트 | 도메인 규칙, 정책 분기, 변환, 예외 처리 | Spring Context·DB 없이 가장 빠르게 검증한다. |
| 웹 계층 테스트 | HTTP 매핑, 인증·인가, 요청 검증, 응답 직렬화 | Controller가 제공하는 웹 계약만 검증한다. |
| 영속성 테스트 | 쿼리 의미, 정렬·필터, 삭제 처리, DB 제약 | 실제 DB/JPA 동작이 판단 근거일 때 사용한다. |
| 통합 테스트 | 트랜잭션 경계, 모듈 연결, 실제 경합 | 단위·웹·영속성 테스트만으로 증명할 수 없을 때 사용한다. |

기본 선택은 순수 단위 테스트다. SQL의 의미, DB 제약, 실제 트랜잭션처럼 해당 계층에서만 검증 가능한 위험이 있을 때만 상위 계층 테스트를 추가한다.

같은 위험을 여러 계층에서 반복 검증하지 않는다. 정책은 단위 테스트, HTTP 변환은 웹 계층 테스트, DB 질의 의미는 영속성 테스트가 주로 소유한다. 계층을 넘는 외부 계약은 필요한 범위에서만 통합 테스트로 보완한다.

## 5. 테스트 대역과 데이터

단위 테스트에서는 DB, 네트워크, 메시지 브로커, 현재 시각처럼 느리거나 비결정적인 의존성을 대역으로 바꾼다. 대역은 테스트하려는 규칙에 필요한 결과만 제공해야 하며, 실제 구현을 다시 작성하는 용도로 사용하지 않는다.

여러 사용자·요청·트랜잭션 간 격리, DB 제약, 동시성 경합은 mock만으로 증명하지 않는다. 실제 저장소 또는 통합 환경이 필요한 검증으로 둔다. 실행 비용이 큰 테스트는 테스트 태그와 CI 정책을 이용해 일반 빠른 검증과 분리하되, 검증 목적과 별도 실행 방법을 함께 남긴다.

현재 `concurrency` 태그 테스트는 실행 환경 부하에 따른 간헐 실패 때문에 기본 CI에서 제외한다. 이 정책은 테스트를 폐기한다는 뜻이 아니며, 동시성 변경 전후에는 아래처럼 CI 제외 조건을 해제해 별도로 실행한다.

```bash
env -u CI ./gradlew :ogonggo-api-user:test --tests '*RecruitmentPostBookmarkConcurrencyTest'
```

## 6. 추가·유지·제거 판단

테스트를 추가하거나 유지하기 전에 아래를 확인한다.

1. 사용자 계약 또는 시스템 불변식이 깨지면 이 테스트가 실패하는가?
2. 단순 리팩터링만으로 깨지는 구현 상세 테스트는 아닌가?
3. 더 빠르고 낮은 계층에서 같은 위험을 검증할 수 있는가?
4. 실제 정책, 변경 요구, 과거 회귀 중 명확한 근거가 있는가?

위 질문에 답할 수 없으면 테스트를 제거하거나, 검증 대상을 행동 계약으로 줄인다. 테스트를 제거할 때는 다른 테스트가 같은 계약을 이미 소유하는지 먼저 확인한다.

## 7. 실행과 변경 완료 기준

변경한 테스트는 먼저 가장 좁은 Gradle 테스트 대상으로 실행한다. 공통 모듈, 공개 API 계약, 영속성 동작을 바꿨다면 영향 모듈까지 검증 범위를 넓힌다. 실행하지 못한 검증은 성공한 것처럼 기록하지 않고, 이유와 남은 위험을 남긴다.

Controller·OpenAPI 계약 변경은 [OpenAPI와 API 계약](openapi.md)의 검증 기준을 함께 따른다. 시간 기반 동작은 [시간 처리](time-handling.md)의 Clock·시간대 규칙을 함께 따른다.
