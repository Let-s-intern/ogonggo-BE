# 오공고 가입 안내·스크랩 채용공고 리마인드 알림톡 PRD

- 작성일: 2026-10-04
- 상태: 통합 알림 테이블 전환 구현 및 모듈 테스트 완료, 사용자 리뷰·운영 반영 전
- 진행 갱신: 2026-10-06
- 대상: 오공고 BE
- 코드 확인 기준: 로컬 원격 추적 브랜치 `origin/main`, `b918d8ca0d22b0391df8e91777eec97d94c19bb9`
- 참고 구현: 렛츠커리어 1:1 라이브 멘토링의 NHN 알림톡 발송 구조
- 문서 범위: 요구사항·구현 방향·인수 기준. 실제 운영 DB 적용·배포·알림 발송 완료를 의미하지 않는다.

## Problem Statement

일반회원은 오공고 가입 완료를 카카오톡으로 안내받지 못하고, 스크랩한 채용공고의 마감 시점을 직접 확인해야 한다. 가입 정보를 확인하고 관심 공고의 지원 시기를 놓치지 않도록 가입 안내와 마감 리마인드가 필요하다.

현재 BE에는 일반회원 최초 가입 판정, 사용자 휴대폰 번호, 채용공고 스크랩, 모집 종료 일시가 있다. NHN 알림톡 발송 코드는 없으므로, 렛츠커리어에서 사용하는 발송 구조를 오공고의 모듈·트랜잭션·스케줄 규칙에 맞게 적용한다.

## Solution

NHN에 등록된 템플릿 두 개를 사용한다. 애플리케이션은 수신번호, 템플릿 코드, 치환 변수 및 중복 방지 키를 `notifications`에 적재하고, 통합 발송 스케줄러가 채널 adapter를 통해 전달한다. 본문·버튼·버튼 URL은 NHN의 고정 설정을 사용하며 애플리케이션에서 생성하거나 수정하지 않는다. 테이블과 채널 adapter 경계는 모든 알림에 공통으로 쓰며, 이번 범위에서 실제 발송을 구현하는 채널은 카카오만이다.

| 구분 | 대상과 발송 계기 | 템플릿 코드 | 전달할 변수 |
| --- | --- | --- | --- |
| 가입 안내 | 일반회원의 오공고 계정이 처음 생성되고 커밋되었을 때 | `sign_up_confirm` | `name`, `userEmail`, `loginType`, `createDate` |
| 스크랩 리마인드 | 스크랩한 채용공고의 모집 마감 일시로부터 정확히 24시간 전 | `clip_remind` | `name`, `posting-title` |

기업회원 가입 안내와 채용공고 이외 콘텐츠의 스크랩 알림은 이번 범위에 포함하지 않는다.

## User Stories

1. 일반회원으로서, 오공고에 처음 가입했을 때 가입 안내를 받아 가입 완료를 확인하고 싶다.
2. 일반회원으로서, 가입 안내에서 이름·가입 이메일·로그인 방식·오공고 가입일을 확인하고 싶다.
3. 기존 일반회원으로서, 재로그인할 때 가입 안내를 다시 받지 않고 싶다.
4. 일반회원으로서, 가입이 취소되거나 저장에 실패했을 때 가입 완료 안내를 받지 않고 싶다.
5. 기업회원으로서, 일반회원 전용 가입 안내의 발송 대상에 포함되지 않고 싶다.
6. 채용공고를 스크랩한 사용자로서, 마감 24시간 전에 알림을 받아 지원할 시간을 확보하고 싶다.
7. 스크랩한 사용자로서, 알림에서 내 이름과 해당 채용공고 제목을 확인하고 싶다.
8. 스크랩을 해제한 사용자로서, 해제가 반영된 공고의 마감 알림을 새로 발송받지 않고 싶다.
9. 스크랩한 사용자로서, 삭제·비공개·이미 마감된 채용공고의 지원 안내를 받지 않고 싶다.
10. 스크랩한 사용자로서, 마감 일시가 없는 공고를 임의의 D-1 대상으로 안내받지 않고 싶다.
11. 사용자로서, 서로 다른 스크랩 채용공고는 각각의 마감 일시에 맞춰 안내받고 싶다.
12. 사용자로서, 동일한 알림을 여러 서버나 중복 이벤트 때문에 반복 수신하지 않고 싶다.
13. 사용자로서, 알림톡 전송 실패 때문에 가입·로그인·스크랩 기능을 사용할 수 없게 되는 일을 피하고 싶다.
14. 운영자로서, NHN에 등록된 본문과 버튼을 그대로 사용해 서버에서 별도의 문구·링크를 관리하지 않고 싶다.
15. 운영자로서, 기존 NHN 설정 이름을 유지하여 설정을 같은 이름으로 이관하고 싶다.
16. 운영자로서, 발송 요청 실패와 발송 제외 사유를 민감정보 없는 로그로 구분하고 싶다.

## Implementation Decisions

### 1. 확정된 제품 요구사항

- 가입 안내는 일반회원만 대상으로 한다.
- 스크랩 리마인드는 채용공고만 대상으로 한다. 부트캠프·스터디·사이드 프로젝트에는 적용하지 않는다.
- 리마인드 예정 시각은 모집 마감 일시에서 정확히 24시간을 뺀 값이다. 전날 특정 시각의 일괄 발송으로 바꾸지 않는다.
- NHN 템플릿 코드와 치환 변수 이름은 위 표와 동일하게 사용한다. 특히 `posting-title`의 하이픈을 유지한다.
- 본문·버튼은 NHN에 등록된 상태 그대로 사용한다. 회사·직무명은 템플릿에 치환 변수가 없으므로 애플리케이션에서 값을 채우지 않는다.
- YAML 설정은 사용자가 직접 이관한다. 실제 설정값이나 발신 키는 PRD·소스·테스트 데이터에 복사하지 않는다.

### 2. 가입 안내

- 가입 완료 알림 행은 가입 커밋 직후 이벤트로 적재한다. 가입 대상 평가에 스케줄러를 붙이지 않지만, provider 실제 발송은 다른 모든 알림과 같이 통합 발송 스케줄러가 맡는다.
- 기존 `UserAuthService`의 신규 계정 판정을 사용한다. 렛츠커리어에 이미 가입한 사람이더라도 오공고 계정이 처음 생성되면 오공고의 신규 가입이다.
- 계정과 프로필을 저장하는 기존 `TransactionTemplate` 안에서 신규 가입 이벤트를 발행하고, `@TransactionalEventListener(AFTER_COMMIT)`에서 별도 가입 적재 실행기에 작업을 넘긴다. provider HTTP 호출은 별도 발송 실행기가 맡는다. 이벤트는 기존 트랜잭션 안에서 발행한다.
- 계정 생성이 롤백되거나 최초 가입 동시 요청 중 저장에 실패한 요청에서는 발송하지 않는다. 기존 가입자의 로그인·토큰 재발급은 발송 계기가 아니다.
- 가입 안내의 기준은 오공고 계정 생성 커밋이다. 후속 토큰 발급 결과를 새로운 가입으로 판정하거나, 재로그인 때 발송을 보충하지 않는다.
- 수신번호 또는 템플릿 필수 변수가 없거나 유효하지 않으면 알림만 생략하고 가입은 성공시킨다. 생략 사유는 민감값 없이 기록한다.
- 수신번호는 국내 `010`으로 시작하는 숫자 11자리 또는 정확한 `010-1234-5678` 형식만 허용하고 하이픈을 제거해 전송한다. 국제번호·다른 식별번호·공백·불규칙한 하이픈은 보정하지 않고 알림만 생략한다. 이름·이메일은 표시 변수이므로 null·공백 여부만 확인한다.

| 변수 | 데이터와 표현 |
| --- | --- |
| 수신번호 | 오공고에 동기화된 `UserProfile.phoneNum` |
| `name` | `UserProfile.name` |
| `userEmail` | `UserProfile.email`. 별도의 정보 수신용 이메일을 사용하지 않는다 |
| `loginType` | `LetsCareerAuthProvider.desc`에 ` 로그인`을 붙인다. 예: `카카오톡 로그인`, `이메일 로그인` |
| `createDate` | 한국 시간 기준으로 저장된 오공고 계정의 `joinedAt` 날짜를 `yyyy-MM-dd` 형식으로 만든다. 예: `2026-10-04` |

### 3. 스크랩 채용공고 리마인드

- 스크랩 리마인드는 모집 마감 24시간 전이라는 미래 시각에 발송한다. 북마크 이벤트 직후 보내는 가입 알림과 달리, 예정 시각에 도달한 대상을 찾을 실행 방식이 필요하다. 현재 제안은 기존 DB 스케줄 작업이 예정 시각이 지난 대상을 조회하는 방식이다.
- `JobBookmark`의 활성 스크랩과 `Job.recruitmentEndAt`을 기준으로 대상자를 조회한다.
- 수신번호는 `UserProfile.phoneNum`, `name`은 `UserProfile.name`, `posting-title`은 `Job.title`을 사용한다.
- 발송 판단에 사용하는 현재 시각은 주입받은 `Clock`에서 한 번 생성한다. 업무 시간대는 `Asia/Seoul`이다.
- 예를 들어 모집 마감이 2026-10-06 17:30이면 예정 시각은 2026-10-05 17:30이다. 마감일의 날짜만 비교하거나 일 단위로 반올림하지 않는다.
- 기본 제외 조건은 비활성 계정(정지·탈퇴), 스크랩 해제, 공고 삭제·비공개·기마감, 모집 마감 일시 없음, 수신번호·필수 치환값 누락이다. 계정은 활성 상태만 대상이다. 지원 관리 상태는 `SCRAPPED`·`PREPARING`만 대상으로 하고, `APPLIED`·`INTERVIEWING`·`PASSED`·`FAILED`는 제외한다.
- 스크랩이 D-1 예정 시각보다 늦게 새로 등록된 경우에는 과거 예정 시각으로 소급 발송하지 않는다. 반면 예정 시각 전에 등록된 활성 스크랩은 스케줄 실행이 늦어져도 due 대상 조회 시간창 안에서 발송한다.
- 이미 리마인드를 받은 뒤 모집 마감 일시가 변경되면, 아직 발송 대기 중인 이전 알림 행을 삭제하고 새 마감 일정을 다시 판단한다. 새 D-1 예정 시각이 미래이고 대상이면 새 알림을 적재하며, 이미 지났으면 소급 발송하지 않는다. 새 notification 행은 새 UUID 고유 키를 갖는다.
- 모집 마감 일시 변경은 이벤트 기반으로 처리한다. 새 일정의 실제 발송은 변경 이벤트에서 즉시 보내지 않고 기존 매분 스케줄러가 새 D-1 예정 시각에 적재한다. 새 예정 시각이 이미 지났다면 새 알림 건을 만들지 않는다.
- `notifications`에 건이 기록되면 발송 대상으로 소비된 것으로 간주한다. 스크랩 해제·계정 상태·공고 상태 변화로는 기존 건을 재검증하지 않는다. 마감 변경만 예외로 해당 공고의 `PENDING` 행을 삭제한다. dispatcher가 이미 행을 읽어 provider 요청을 시작했다면 취소를 보장하지 않으며 이전·새 알림이 모두 발송될 수 있다.
- 대상 여부는 매분 스케줄러가 due 대상을 평가할 때의 현재 상태로 결정한다. 그 실행 시 활성 스크랩이며 `SCRAPPED` 또는 `PREPARING`이면 대기열에 넣고, 아니면 발송 건을 만들지 않는다. 이후 재스크랩 이벤트로 과거 대상을 보충하지 않는다.
- 대상 조회는 매분 스케줄러 평가 시점의 최신 상태를 확인한다. `notifications` 기록 뒤 일반 상태 재검증은 하지 않지만, 마감 변경 때는 위 취소 정책을 적용한다. `SENT`는 provider 접수 결과이지 실제 도착이 아니다.
- 서로 다른 사용자와 서로 다른 채용공고는 각각 독립된 알림 대상이다.

### 4. 모듈과 공개 계약 — 구현 제안

앞서 제시한 구성요소를 이번 두 알림에 필요한 범위로 적용한다. 아래의 클래스 배치와 테스트 범위는 구현 제안이며, 제품 요구사항과 구분한다.

| 구성요소 | 소유 모듈 | 책임과 계약 |
| --- | --- | --- |
| NHN 전송부 | `ogonggo-api-user` | 사용자 API가 소유하는 외부 연동으로, 수신번호·템플릿 코드·치환값·중복 방지 키를 받아 요청을 전송하고 결과를 판별한다 |
| 가입 이벤트와 알림 처리 | `ogonggo-api-user` | 신규 일반회원 판정, 커밋 후 처리, 가입용 변수 구성 |
| 리마인드 대상 Reader | `ogonggo-core` | 공고·활성 스크랩·사용자 프로필을 조회하여 필요한 값만 DTO로 제공한다 |
| 리마인드 실행과 정책 | `ogonggo-api-user` | 예정 시각 계산, 발송 대상 판단, 변수 구성, 공통 전송부 호출 |
| 공통 알림 행·상태·중복·발송 결과 | `ogonggo-core/notification` | `PENDING`·`SENT`·`FAILED`, 예약 시각, provider 최종 결과 관리 |
| 사용자 API 알림 대상 적재·provider adapter | `ogonggo-api-user` | 가입/리마인드 정책 및 Kakao sender 구현. NHN 설정은 API 소유 |
| 발송 실행 | `ogonggo-api-user` | `NotificationDispatcher`가 ShedLock 아래 due 행을 읽고 channel sender로 전달 |

- 참조 구현의 `NhnProvider`, `NhnFeignController`, `NhnSecretKeyReader` 및 요청·응답 DTO 이름을 유지하는 방향으로 Kotlin에 이식한다. OpenFeign 의존성과 활성화 설정은 `ogonggo-api-user`에만 둔다.
- 전송부는 오공고의 `User` 엔티티를 직접 받지 않고 발송에 필요한 값만 받는다. NHN에 전달할 요청 구성·응답 판단을 한 경계 안에서 검증할 수 있게 한다.
- API Service와 API Implement는 core Repository를 직접 참조하지 않고 core의 공개 계약을 사용한다.
- DB 조회·DTO 구성과 외부 HTTP 호출을 분리하여 NHN 응답을 기다리는 동안 DB 트랜잭션을 유지하지 않는다. 비동기 스레드로 JPA 엔티티를 넘기지 않는다.
- 가입 notification 적재와 provider 발송은 서로 다른 전용 실행기를 사용한다. 포화 시 가입은 성공으로 유지하며 알림을 건너뛰고 집계 가능한 로그를 남긴다. provider 실행기 포화 시에는 남은 행을 `PENDING`으로 두고 요청 스레드에서 대신 발송하지 않는다.
- 알림톡 연동은 사용자 API의 구현이다. core 및 관리자 API에 Feign 의존성, 필수 NHN 설정, 발송 작업을 추가하지 않는다.
- 새로운 사용자·관리자 HTTP API는 추가하지 않는다. 기존 가입·로그인·스크랩 API의 계약을 유지한다.

### 5. 설정 및 NHN 요청

| 유지할 설정 이름 | 용도 |
| --- | --- |
| `nhn.appKey` | NHN 프로젝트 식별 |
| `nhn.secretKey` | NHN 인증 헤더 구성 |
| `nhn.sendKey` | NHN 템플릿의 발신 프로필 지정 |
| `nhn.templateCode` | 기존 설정과의 이름 호환. 이번 두 알림은 각 기능에 지정된 템플릿 코드를 전달한다 |

- 참고 구현은 `X-Secret-Key` 인증 헤더와 `X-NC-API-IDEMPOTENCY-KEY` 중복 방지 헤더를 사용한다. 이 요청 구조를 유지한다.
- NHN 요청에는 본문·버튼·버튼 URL을 생성해서 넣지 않는다. 승인된 템플릿과 치환값을 사용한다.
- 실제 키 값, 수신번호, 이메일, 전체 요청·응답 본문을 로그에 출력하지 않는다. NHN 응답에 수신번호가 포함될 수 있으므로 참조 구현의 전체 응답 출력은 그대로 복제하지 않는다.
- 환경별 실제 설정값은 사용자가 관리한다. 개발·테스트 검증에는 가짜 값과 HTTP 대역을 사용한다.

### 6. 스케줄·중복 방지·실패 처리

- 이 절의 스케줄 정책은 채용공고 스크랩 리마인드에만 적용한다. 가입 완료 알림은 커밋 후 이벤트 기반으로 처리하며 스케줄러를 사용하지 않는다.
- 리마인드 작업은 기존 `ScheduledJobDefinition`, `scheduled_jobs`, ShedLock 구조를 사용하는 안이다. 참고 서버의 Spring Batch 전체를 복제하지 않는다.
- 실행 주기·켜짐 여부는 기존 DB 스케줄 관리 방식을 따른다. 이번 PRD에서는 새로운 YAML 스케줄 설정을 요구하지 않는다.
- 스케줄 등록기의 DB 설정 새로고침은 1분 주기지만, 이것은 작업 실행 주기가 아니다. 각 작업의 실행 빈도는 `scheduled_jobs.cron`이 정한다.
- 예정 시각 이전에는 발송하지 않는다. 실제 NHN 요청 시각은 실행기·조회·통신 지연의 영향을 받고, 최종 메시지 도착 시각은 외부 발송 시스템에도 의존한다.
- 사용자는 예정 시각 이후 스케줄 실행 지연이 발생할 수 있음을 허용했다. "정확히 24시간 전"은 여전히 예정 시각 계산에 적용한다.
- 신규 리마인드 작업은 매분(`0 * * * * *`) due 대상을 조회해 발송 대기열에 적재한다. 이는 이 작업의 cron이며 다른 기존 작업의 실행 주기를 뜻하지 않는다. 매분 조회가 사용자에게 1분 내 도착을 보장하지는 않는다.
- 모집 마감 일시 변경 이벤트는 이전 `PENDING` notification 행을 삭제하고 새 일정을 반영한다. dispatcher가 이미 provider 요청을 시작했다면 취소를 보장하지 않는다. NHN에 즉시 발송하지 않고 새 D-1 예정 시각은 매분 due 조회가 처리한다.
- MAU 5만을 보수적 규모 참고치로 삼는다. 사용자가 부하테스트를 제외하기로 결정했으므로 피크 분당 5만 건 처리량·backlog·지연은 측정하지 않으며 처리 보장도 하지 않는다.
- 스케줄 작업은 due 대상 전체를 발송하지 않고 페이지 단위로 조회해 리마인드 발송 대기열에 넣는다. 각 새 리마인드 행은 UUID 고유 키와 `clip-remind:job:{jobId}:` 접두어를 갖는다. 알림 적재와 페이지 커서 갱신은 한 트랜잭션으로 처리하므로 페이지 재시도 후 중복 행이 남지 않는다. 일정 테이블은 공고·마감일별 한 행만 유지한다. 각 페이지 조회 당시의 자격으로 대상을 한 번 판단하고, 커서가 지난 스크랩 ID는 이후 자격 상태가 바뀌어도 같은 일정에서 다시 조회하지 않는다.
- 다중 인스턴스 발송은 delivery scheduler 전체에 최대 90초 ShedLock을 걸어 한 실행만 due `PENDING` 행을 읽게 한다. 각 실행은 전용 4-thread 실행기로 최대 4건씩 병렬 요청하고 최대 45초 동안 처리한다. NHN 전송 요청은 DB 트랜잭션 안에서 실행하지 않는다.
- 2026-10-06 단순화 결정: 알림 상태는 `PENDING → SENT/FAILED`로 제한한다. 행별 `PROCESSING` claim, claim timeout·recovery, 자동 retry 횟수·백오프·cutoff는 구현하지 않는다. 발송 오류 응답은 모두 `FAILED`와 `result_code`로 기록한다.
- `SENT`는 NHN provider 접수 확인을 뜻하고 최종 사용자 도착과 구분한다. NHN `-1005` 중복 키 응답은 접수 확인이 아니므로 `FAILED`로 기록한다. 동일 deduplication key에서 파생한 NHN 멱등성 키로 10분 이내의 우발적 중복 호출을 억제한다.
- `FAILED` 건은 자동 재시도하지 않는다. 단, 프로세스가 NHN 접수 후 결과 저장 전에 종료되거나 결과 저장에 실패하면 행은 `PENDING`으로 남아 다음 scheduler 실행에서 다시 호출될 수 있다. 이런 미확정 행이 생긴 실행은 같은 run에서 즉시 반복하지 않는다. 10분 멱등성 창을 넘긴 뒤 다시 호출되면 중복 발송 가능성이 있다. 별도의 복구 상태·retry counter를 두지 않는 단순화의 트레이드오프로 수용한다.
- 실행 로그는 run ID, 소요 시간, 적재·발송 건수와 비민감 오류 유형을 남긴다. provider 거절·최종 실패는 채널과 `resultCode`, 잠금 미취득은 scheduler 이름으로 집계할 수 있게 한다. 연락처·템플릿 변수는 제외한다.
- 가입 커밋 후 listener는 별도의 단일 스레드·유한 큐 실행기에 적재 작업을 제출한다. provider 발송 실행기와 격리하며, 커밋 후 적재 전 프로세스 종료·큐 포화·DB 오류에 따른 드문 유실은 사용자가 수용했다. 실패는 가입 성공을 되돌리지 않고 로그로 추적한다.
- 가입은 사용자별 고정 키로 이벤트 중복 적재를 막고, 리마인드는 적재마다 새 UUID 키를 저장한다. 리마인드 행과 페이지 커서는 한 트랜잭션에서 함께 갱신된다. 리마인드 일정은 ShedLock과 저장된 커서로 이어 처리하며 별도 `PROCESSING` 상태를 두지 않는다.
- ShedLock의 작업 실행 제어와 NHN의 요청 중복 방지는 구분한다. 키를 전달한다는 사실만으로 영구적인 1회 발송이나 장애 후 복구를 보장하지 않는다.
- 가입 이벤트용 업무 트랜잭션 내 범용 outbox와 운영자 수동 재발송 기능은 범위에 넣지 않는다. 두 알림 모두 `notifications`에 적재하고 자동 재시도하지 않는다.
- HTTP 성공 여부뿐 아니라 NHN 응답의 성공 여부와 수신자별 접수 결과를 확인한다. 발송 요청 접수를 최종 사용자 수신 성공으로 기록하지 않는다.
- 발송 불가 데이터는 제외 사유를 기록하고, 전송 실패는 민감값을 제거한 진단 정보로 기록한다. 한 수신자의 실패가 다른 수신자 처리를 중단하거나 가입·로그인·스크랩 결과를 실패로 바꾸지 않게 한다.
- 현재 확보한 사용자·프로필·공고·스크랩 데이터를 우선 사용한다. 새 업무 도메인 테이블은 추가하지 않으며, 알림 상태는 공통 `notifications`, 일정 커서는 리마인드 전용 일정 테이블에 저장한다.

## Testing Decisions

테스트는 내부 메서드 호출 순서나 클래스 분리를 고정하지 않고, 대상 선정·외부 요청·커밋 경계·실패 격리라는 관찰 가능한 동작을 검증한다. 구현 및 실행 현황은 아래 개발 체크리스트에 표시한다.

| 검증 대상 | 인수 기준 | 권장 계층 |
| --- | --- | --- |
| 신규 가입 | 일반회원 계정 생성 커밋 후 가입 요청이 발생하고, 재로그인·기업회원 가입·롤백에는 발생하지 않는다 | 정책 단위 테스트 + 실제 트랜잭션 통합 테스트 |
| 가입 변수 | 가입 이메일, 가입 경로의 표시명, 한국 시간 `yyyy-MM-dd` 형식의 오공고 가입일을 사용한다 | 순수 단위 테스트 |
| NHN 요청 | 두 템플릿의 변수 키가 정확하고 `posting-title`을 변경하지 않으며, 본문·버튼을 추가하지 않는다 | 직렬화·HTTP 계약 테스트 |
| 수신 데이터 누락 | 번호·필수 변수 누락 시 외부 호출 없이 제외되고 본래 업무는 성공한다 | 단위 테스트 |
| 예정 시각 | 마감 일시에서 24시간을 빼며, 월·연도 경계에서도 동일하고 예정 시각 이전에는 보내지 않는다 | 고정 `Clock` 단위 테스트 |
| 늦은 스크랩 | D-1 예정 시각을 지난 뒤 등록된 스크랩은 소급 발송하지 않지만, 그 전에 저장된 활성 스크랩은 예정 시각 이후 스케줄 지연으로 처리될 수 있다 | 고정 `Clock` + 영속성 테스트 |
| 스크랩 대상 | 활성 스크랩 중 `SCRAPPED`·`PREPARING`만 선택하고 나머지 지원 단계, 삭제·비공개·기마감·마감 일시 없음 및 비대상 콘텐츠는 제외한다 | 실제 DB/JPA 조회 테스트 |
| 반복·경합 | 가입은 고정 키로 같은 가입을 중복 적재하지 않는다. 리마인드는 페이지 적재·커서를 한 트랜잭션으로 처리하고 각 notification에 UUID 키를 부여한다. 커서가 지난 뒤 자격이 바뀐 스크랩은 같은 일정에서 재평가하지 않는다 | 단위 테스트 + 페이지 경계 영속성 테스트 |
| 실패 격리 | NHN 오류·타임아웃·실패 응답·빈 응답이 성공으로 처리되지 않고 다른 수신자 및 가입 결과를 훼손하지 않는다 | HTTP 대역·비동기 통합 테스트 |
| 실행 경계 | 가입 커밋 후 알림 행을 적재하고, 포화 시 요청 스레드에서 provider를 직접 부르지 않으며 적재 오류가 가입 응답을 실패로 바꾸지 않는다 | 트랜잭션·서비스 테스트 |
| 통합 발송 | dispatcher가 채널 sender를 선택하고, 구현되지 않은 채널은 접수 성공으로 오인하지 않는다 | dispatcher 단위 테스트 |
| 공통 알림 대기열 | 같은 dedup key는 한 행만 남고, dispatcher는 ShedLock으로 다중 인스턴스 실행을 직렬화하며, 접수·실패와 PII 삭제가 구분된다 | 실제 DB 통합 테스트 |
| 피크 처리 | 사용자가 부하테스트를 제외하기로 결정했다. 5만 due 건의 처리량·backlog·지연은 미측정이며 보장하지 않는다 | 미실시(합의된 제외) |
| 로그 | 가입 적재 실패·최종 발송 실패·provider 거절·ShedLock 미취득을 집계할 필드를 남기고 민감값은 노출하지 않는다 | 단위 테스트·HTTP 대역·공유 DB 잠금 테스트 |

기존 `UserAuthServiceTest`의 신규·기존 가입자 분기, `JobAutoCloseSchedulerTest`의 고정 Clock, `ScheduledJobRegistrarTest`의 작업 등록 테스트를 참고한다. 공통 상태·SQL 조건은 core 영속성 테스트, provider 요청은 HTTP 대역, 업무별 적재는 API 단위·트랜잭션 테스트로 나눠 같은 위험을 여러 계층에서 중복 검증하지 않는다.

시간 경계, 마감 변경, 늦은 스크랩, 발송 성공·실패와 대상 조회의 관련 테스트를 작성하고 실행했다. 남은 인수 테스트와 실행 범위는 아래 체크리스트에 표시한다. 실제 NHN 발송과 부하테스트는 자동화 검증에 포함하지 않는다.

2026-10-05 기존 리마인드 구현 검증 결과:

- `./gradlew :ogonggo-core:test --tests '*JobBookmarkReminder*'` — 통과
- `./gradlew :ogonggo-api-user:test --tests '*AlimTalk*' --tests '*JobBookmarkReminder*' --tests '*UserScheduledJobConfigurationTest'` — 통과
- `./gradlew :ogonggo-api-user:test --tests '*SchedulerLockConfigurationTest' --tests '*SchedulerLockIntegrationTest' --tests '*UserScheduledJobConfigurationTest'` — 통과
- 운영 키·실제 수신번호를 사용한 발송은 실행하지 않았다.

## Development Checklist

개발은 아래 순서로 진행한다. 00은 동작 합의를 위한 리뷰 단계라 코드 커밋을 만들지 않는다. 01–03은 각각 독립적으로 실행 가능한 범위까지 완성하고 하나씩 커밋한다. 각 커밋 뒤 사용자가 동작과 diff를 리뷰하고, 수정 요청을 반영한 뒤 다음 단위로 간다.

각 구현 단위 안에서는 아래의 짧은 TDD 반복을 하나씩 적용한다. 모든 테스트를 먼저 작성하거나 한꺼번에 구현하지 않는다.

1. 다음에 확인할 관찰 가능한 동작 하나를 테스트로 적는다.
2. 테스트를 실행해 의도한 동작이 없어 실패하는지 확인한다.
3. 그 동작만 통과할 최소 코드를 작성하고 테스트를 통과시킨다.
4. 초록 상태에서만 리팩터링하고 해당 테스트를 다시 통과시킨다.

- [x] `EMAIL`, `FCM` enum 및 sender extension point만 준비한다. 실제 이메일·푸시 adapter, FCM 토큰 등록은 이번 범위에서 구현하지 않는다.
- [x] 최초 배포 SQL은 북마크 활성 시각, 리마인드 일정, `notifications`를 한 번에 생성한다. 이 브랜치의 기능은 미배포 상태이므로 구 `job_bookmark_reminders` 데이터 이관은 하지 않는다.
- [x] Mermaid 설계 가이드와 PRD의 구현 결정을 공통 테이블·스케줄러 소유 구조에 맞춰 갱신한다.
- [ ] 단순화 후 영향 모듈의 관련 Gradle 테스트와 컴파일을 다시 실행한다.
- [ ] 작업 트리의 기존 변경과 범위를 분리해 diff를 사용자 리뷰하고, 승인된 작업 단위로 커밋한다.

### 이후 커밋의 완료 조건

- 해당 단위의 동작을 먼저 실패 테스트로 확인한 뒤 최소 구현으로 통과시킨다.
- 테스트는 구현 내부가 아니라 사용자 또는 호출자가 관찰하는 계약을 검증한다.
- 관련 Gradle 테스트와 컴파일 검증 결과, 실행하지 못한 항목과 이유를 리뷰에 남긴다.
- 운영 설정 값·실제 연락처·실제 NHN 요청을 diff나 테스트 로그에 넣지 않는다.
- 요청 범위 밖의 기존 작업트리 수정과 문서는 스테이징하지 않는다.
- 사용자가 리뷰할 수 있도록 커밋 하나에는 논리적 작업 단위 하나만 포함한다.

## 운영 반영 전 체크리스트

실제 비밀값은 이 문서나 소스에 기록하지 않는다. 운영자가 각 항목을 확인한 뒤 스케줄을 활성화한다.

- [ ] NHN YAML/환경 설정에 `nhn.appKey`, `nhn.secretKey`, `nhn.sendKey`, `nhn.templateCode`를 기존 이름 그대로 이관하고, 사용자 API에서 설정 누락 없이 시작되는지 확인한다.
- [ ] NHN에 `sign_up_confirm`·`clip_remind` 템플릿과 발신 프로필이 승인·사용 가능한지 확인한다. 본문과 버튼은 NHN 등록본을 사용한다.
- [ ] DB 백업과 현재 main 기준 스키마를 확인한 뒤 [최초 알림 기능 마이그레이션](../schema/2026-10-06-notifications.sql) 하나만 사용자 API 배포 전에 적용한다. 기존 리마인드 큐 테이블은 이 브랜치에서만 만들었고 한 번도 배포되지 않았으므로 생성·이관하지 않는다.
- [ ] 마이그레이션이 `jobBookmarkAlimTalkReminder` (`0 * * * * *`)와 `jobBookmarkAlimTalkDelivery` (`* * * * * *`) 행을 비활성으로 생성했는지 확인한다. 기존 행은 `insert ignore`와 코드 규칙에 따라 덮어쓰지 않는다.
- [ ] 배포 후 설정·스키마·대상 일정과 `notifications` 상태를 확인하고, 실제 발송이 승인된 시점에 두 작업을 활성화한다. 전체 발송 중지는 적재·발송 작업을 모두 비활성화한다. 적재만 끄면 이미 적재된 알림 발송은 계속된다.
- [ ] 활성화 후 적재·dispatcher 실행 로그와 `PENDING`·`SENT`·`FAILED` 상태를 관찰한다. `SENT`는 NHN 접수이며 최종 사용자 수신을 뜻하지 않는다.
- [ ] 부하테스트는 사용자 결정으로 제외됐다. 5만 due 건의 처리량과 backlog 해소 시간은 확인되지 않았으므로 용량 보장으로 간주하지 않는다.

## Out of Scope

- 기업회원 가입 안내와 부트캠프·스터디·사이드 프로젝트 리마인드
- NHN 템플릿 등록·수정·심사, 본문·회사명·직무명·버튼·URL의 동적 생성
- 실제 이메일·FCM provider adapter, 푸시 토큰 등록 API/저장 및 각 채널 템플릿 구성. 공통 테이블과 enum 경계만 준비하며, sender가 없는 채널은 적재하지 않는다.
- 문자 대체 발송과 앱 내 알림함
- 알림 수신 설정 UI/API, 관리자 수동 발송·재발송 화면
- 가입 이벤트의 업무 트랜잭션 내 범용 outbox와 최종 도착 결과 콜백. 커밋 후 알림 행 적재 전 프로세스 종료에 따른 드문 가입 알림 유실은 사용자가 수용했다.
- Kafka·Redis 같은 별도 메시지 브로커. 우선 DB 대기열·페이지 조회·제한 동시성 worker를 사용한다.
- 이미 가입한 회원에게 가입 안내 일괄 소급 발송
- 실제 자격증명 조회·복사, 운영 DB 변경, 배포, 실제 알림톡 발송
- 참고 렛츠커리어 서버의 코드 수정

### 확정 정책 기록

아래 항목은 구현 중 합의한 정책을 보존한다. 추가 템플릿 정보나 미결 제품 결정을 뜻하지 않는다.

| 항목 | 확정 내용 |
| --- | --- |
| 발송 정밀도 | 예정 시각은 모집 마감 - 24시간으로 고정하고, 리마인드는 매분 due 대상을 읽어 발송 대기열에 적재한다. 스케줄 등록기의 설정 새로고침 주기와 작업 cron은 다르다. 실제 발송·도착 시간은 실행기·통신·NHN 처리에 좌우된다 |
| 늦은 스크랩 | 확정: D-1 예정 시각 이후의 신규 스크랩은 소급 발송하지 않는다. 예정 시각 이전 등록분의 늦은 스케줄 실행은 허용한다 |
| 계정 상태 | 확정: 스케줄러 평가 시 활성 계정만 대상으로 하고 정지·탈퇴 계정은 제외한다 |
| 공고 공개·모집 상태 | 확정: 스케줄러 평가 시점에 공개·모집 중인 공고만 대상으로 하고 비공개·마감 공고는 제외한다 |
| 지원 진행 상태 | 확정: `SCRAPPED`·`PREPARING`만 발송하고 `APPLIED`·`INTERVIEWING`·`PASSED`·`FAILED`는 제외한다 |
| 커서 이후 대상 상태 변경 | 확정: 각 페이지 조회 당시의 자격으로 한 번 판단한다. 커서가 지난 스크랩 ID의 지원 상태 등 대상 자격이 나중에 바뀌어도 같은 일정에서 다시 조회하지 않는다 |
| 마감 변경 | 확정: 이벤트에서 이전 `PENDING` notification 행을 삭제한다. dispatcher가 이미 읽은 in-flight 요청은 취소를 보장하지 않는다. 새 D-1은 미래이고 대상일 때만 매분 due 스케줄러가 적재한다. 일정은 공고·마감일별 한 행이고 재활성화 시 행을 재사용한다. |
| notification 기록 후 상태 변경 | 확정: 스크랩·계정·공고의 일반 상태 변화는 재검증하지 않는다. 마감 변경만 예외로 이전 `PENDING` 행을 삭제한다. |
| 재스크랩 | 확정: 별도 재스크랩 이벤트는 없고 매분 스케줄러 평가 시점의 due 여부와 활성 상태로 결정한다. D-1 이후 복구된 행은 소급 발송하지 않는다 |
| NHN 재시도 | 확정(2026-10-06 단순화): 자동 재시도·백오프는 구현하지 않는다. NHN 멱등성 키는 같은 논리 알림의 짧은 시간 내 우발적 중복 호출을 억제하는 용도로만 사용한다 |
| NHN 오류 분류 | 확정: provider 거절, 통신 오류, HTTP 응답·해석 실패는 모두 `FAILED` 및 `result_code`로 기록한다. `-1005`는 접수 확인이 아니므로 `FAILED`다 |
| 장애·재시작 | 가입 메모리 이벤트는 프로세스 비정상 종료 시 유실될 수 있으며 사용자가 이 드문 유실을 수용했다. provider 접수 직후 DB 결과 기록 전에 프로세스가 종료되면 행이 `PENDING`으로 남아 다시 읽힐 수 있다. 같은 NHN 키의 10분 보호 이후에는 중복 발송 가능성을 수용한다. `PROCESSING` 복구 상태는 두지 않는다 |
| 공통 발송 시간대 | 확정(2026-10-06): `01:00–08:00` 제한을 철회한다. 예정 시각이 되면 시간대와 무관하게 처리한다 |
| notification 보관 | 확정(2026-10-06): `SENT`·`FAILED` terminal 행은 마지막 상태 변경 후 30일이 지나면 매일 03:30 정리 작업이 500건씩 삭제한다. `PENDING`은 자동 정리하지 않으며, 마감 변경으로 무효화되면 삭제한다 |
| 정리 후 중복 | 확정(2026-10-06): 30일 지난 행을 삭제하면 deduplication key도 사라진다. 이후 같은 업무 이벤트가 다시 들어와 중복 적재될 가능성을 허용하며 별도 tombstone은 두지 않는다 |
| provider 결과 범위 | 확정(2026-10-06): `SENT`는 provider 접수만 뜻한다. NHN→Kakao 구간 실패 및 최종 사용자 도착은 조회 API나 webhook을 연결하지 않는 한 추적 범위 밖이다 |
| 채널별 확장 | 확정(2026-10-06): `NotificationDispatcher`는 공통 흐름을 유지하고 `NotificationSender` 구현체가 채널별 요청·오류 분류를 맡는다. 자동 재시도는 현재 범위가 아니다 |
| 발송 직렬화 | 확정(2026-10-06): 행별 claim 대신 dispatcher 실행 전체에 ShedLock을 적용해 다중 인스턴스를 직렬화한다. 리마인드 일정도 저장 커서를 이용하며 `PROCESSING` 상태를 쓰지 않는다 |

### 근거와 작업 기준

- 제품 범위·템플릿 변수·고정 본문과 버튼 사용은 이 대화에서 사용자가 지정한 내용을 반영했다. 실제 발신 프로필 값은 의도적으로 싣지 않았다.
- 로컬에서 확인한 `origin/main`은 앞서 확인했던 `7258e2e`에서 `b918d8c`로 갱신되어 있다. 두 커밋 사이 변경은 README와 고용 형태 SQL이며, 이 PRD가 참조한 알림 관련 코드의 차이는 없다.
- 현재 체크아웃은 별도 기능 브랜치이고 기존 테스트 수정이 있다. 이 문서 작성에서는 브랜치를 전환하거나 해당 수정을 변경하지 않는다. 구현 시에는 최신 main 기준과 작업 중 변경의 보존을 함께 확인한다.
- 참고 코드의 NHN 응답 전체 출력, 엔티티의 비동기 전달, 배치 구성을 그대로 복사하지 않고 오공고 규칙에 맞춘다.
- 이 저장소에는 PRD 게시용 이슈 트래커·라벨 설정이 없어 로컬 문서로 작성했다. 외부 이슈 등록과 `ready-for-agent` 라벨 적용은 수행하지 않았다.
